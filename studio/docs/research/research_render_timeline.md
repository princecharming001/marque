# Rendering engine and timeline representation for Yunicorn's agentic talking-head editor

## Summary
Recommendation: use Remotion as the single compositor, but treat it as the graphics layer only. Plain ffmpeg/libplacebo steps run before it (HDR-to-SDR conversion, fixed frame rate, clean audio) and after it (sample-accurate audio mix, loudness, final per-platform encode). Remotion's quality problems come from its default settings, not its design: JPEG intermediate frames at quality 80, a BT.601 color matrix by default in v4, no HDR, and audio that arrives about 43 ms late (an open bug). Every one of these can be set or worked around. HyperFrames (HeyGen, Apache-2.0, very active) is the strongest alternative. It is the only engine with real HDR10 compositing, but it is 6 months old. MoviePy, Editly, Motion Canvas/Revideo, GES and MLT are weaker or stale for rich social edits. Shotstack/Creatomate give less control over quality. Deliver 8-bit H.264 SDR BT.709 at 1080x1920, at the source frame rate, inside each platform's published limits. Uploading HDR is unreliable. The timeline should be an app-owned typed JSON document edited through ID-addressed operations. It compiles to a frame-quantized render plan that every consumer reads: the renderer, the audio graph, the iOS preview and the OTIO/FCPXML exporters. Agent-authored motion graphics go in as sandboxed items with parameter schemas.

## Verified findings
## 0. Baseline (verified locally)
Yunicorn currently renders on Remotion Lambda with H.264, `crf: 17`, `imageFormat` jpeg (env-tunable), `jpegQuality: 95` and no `colorSpace`. A code comment blames q80 JPEGs for "caption halos" (`/Users/home/Marque/render/src/lambda-render.ts`). `remotion` is `^4.0.0`. The iOS editor is a second renderer: AVMutableComposition plus native overlays. Prior notes still hold: OTIO and FCPXML are export formats only, and edits are ID-addressed operations on an app-owned document.

## 1. Engines, output quality only

**Remotion** (60.8k stars, v4.0.529 on 2026-09-25; GitHub API). Verified defaults:
- `imageFormat` jpeg at quality 80 ([renderMedia](https://www.remotion.dev/docs/renderer/render-media)).
- CRF 18, x264 preset `medium`, AAC 320k ([crf.ts](https://github.com/remotion-dev/remotion/blob/main/packages/renderer/src/crf.ts); [x264-preset](https://github.com/remotion-dev/remotion/blob/main/packages/renderer/src/options/x264-preset.tsx)).
- `colorSpace` is `default` (= bt601) in v4 and becomes bt709 only under the v5 flag ([color-space.tsx](https://github.com/remotion-dev/remotion/blob/main/packages/renderer/src/options/color-space.tsx)).

The [Quality guide](https://www.remotion.dev/docs/quality) says to use bt709, PNG, `--scale` for text crispness, and the x264 preset.

Known issues:
- **JPEG + bt709 miscolor.** Fixed by [PR #11331](https://github.com/remotion-dev/remotion/pull/11331), merged 2026-09-18. It first shipped in **v4.0.527 (2026-09-22)**. Pin ≥4.0.527.
- **AAC lag.** [Issue #11704](https://github.com/remotion-dev/remotion/issues/11704) reports audio 2048 samples (42.7 ms) late: libfdk_aac priming is lost through an ADTS intermediate. It has a clean ffmpeg repro, but it is **one day old, from a third party, with no maintainer response**. The proposed fix, [PR #11705](https://github.com/remotion-dev/remotion/pull/11705), writes an **MP4 edit list** (`elst media_time=2048`). Instagram and YouTube both say no edit lists (§4), so the upstream fix does not produce platform-compliant files.
- **Volume automation.** The FFmpeg path compiles volume into a per-video-frame, piecewise-constant `volume` expression evaluated per frame. Gain steps every 33 ms at 30 fps, with no interpolation ([source](https://github.com/remotion-dev/remotion/blob/main/packages/renderer/src/assets/ffmpeg-volume-expression.ts)). That risks zipper noise on ducks and fades.
- **HDR.** None: "headless Chrome… does not support HDR", and tagging bt2020 "was a mistake" ([HDR](https://www.remotion.dev/docs/hdr)).
- **Video extraction.** `<OffthreadVideo>` extracts BMP by default and PNG when `transparent`. Its `toneMapped` (zscale) defaults to true and is on/off only ([OffthreadVideo](https://www.remotion.dev/docs/offthreadvideo)).
- **`@remotion/media <Video>`** (Mediabunny) is now the recommended component. It does not preserve pitch on speed changes ([Video](https://www.remotion.dev/docs/media/video)), and it recently misdecoded full-range BT.470BG as limited BT.709 ([#10841](https://github.com/remotion-dev/remotion/issues/10841), fixed 2026-08-26). **Keep OffthreadVideo for final renders** until frame-diff parity passes.
- **License** (confirmed). Free for individuals and companies of up to 3 people. Creators $25/seat/mo with a 3-seat minimum; Automators $0.01/render with a $100/mo minimum; Enterprise from $500/mo ([license](https://www.remotion.pro/license)).
- **Agent tooling.** Official [remotion-dev/skills](https://github.com/remotion-dev/skills) (4.7k stars) plus JIT compilation for AI templates ([JIT](https://www.remotion.dev/docs/ai/dynamic-compilation)).

**HyperFrames** (Apache-2.0, 53.7k stars, created 2026-03-10, v0.8.81 on 2026-09-27; confirmed).
- **Presets:** draft CRF 30, **looks CRF 16 (local default)**, delivery/high CRF 12. `--video-frame-format auto|jpg|png`; ProRes 4444 for MOV ([CLI](https://hyperframes.heygen.com/packages/cli)).
- **Capture path.** HeyGen's write-up says it **pre-extracts every `<video>` into numbered JPEGs** and captures beginFrame screenshots at **JPEG quality 80**. Capture is deterministic only on Linux chrome-headless-shell ([HeyGen](https://www.heygen.com/research/html-to-video)). In the default path, source footage goes through JPEG twice. "Same SDR ceiling as Remotion" is therefore **unproven**; test it in png mode.
- **HDR:** 10-bit HEVC MP4 only. The SDR DOM layer is converted into the HDR color space and composited. No Lambda/Cloud Run, no combining with supersampling, and hardware H.265 lacks static mastering metadata, so use libx265 ([HDR](https://hyperframes.heygen.com/guides/hdr)).
- **Positioning.** Its own docs say Remotion is "older and much more established" and that HyperFrames is "built for an AI agent to author" ([vs Remotion](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion)).

**FFmpeg** (confirmed in the [filters doc](https://ffmpeg.org/ffmpeg-filters.html)).
- `amix` normalize is on by default.
- libplacebo applies the DV RPU by default, and with DV it "will always output BT.2020+PQ" unless you set bt709 output explicitly.
- `peak_detect` is on by default; turn it off "if exactly reproducible frame-perfect results are needed".
- Tone-mapping choices include `bt.2390`, `st2094-40` and `hable`. `contrast_recovery` defaults to 0.30 and may ring.
- libplacebo is Vulkan-based, so it needs a GPU or a software Vulkan driver.
- Weak spots for graphics: zoompan's whole-pixel jitter (practitioner report, plausible) and libass motion limits ([ASS tags](https://aegisub.org/docs/latest/ass_tags/)). Use FFmpeg before and after the compositor, not as the compositor.

**Others (freshness verified).**
- MLT v7.40 (2026-06-25); Shotcut 26.6.25 adds an HDR preview window and HDR export.
- MoviePy v2.2.1 (2025-05-21); [#2395](https://github.com/Zulko/moviepy/issues/2395) is a speed regression, not a quality one.
- Editly: last code commit 2025-02-20. Motion Canvas: last code commit 2025-02-16 (a docs-only commit on 2026-07-02). Revideo moved to midrender/revideo.
- Shotstack has **five** presets, verylow to veryhigh (default medium), and no CRF, bit depth or HDR control ([API](https://shotstack.io/docs/api/)).

**Engine options the researcher missed:**
- **Lottie/Rive** for templated motion graphics that render natively in the iOS editor (lottie-ios Apache-2.0, 26.9k stars; rive-ios MIT) and in Remotion ([@remotion/lottie](https://www.remotion.dev/docs/lottie), [@remotion/rive](https://www.remotion.dev/docs/rive)). This gives preview parity without a WKWebView. Pixel parity is untested.
- **IMG.LY CE.SDK** (commercial) runs the same engine on iOS and on a headless server renderer. It is the only off-the-shelf route to true device/server parity, but it gives up arbitrary CSS/React graphics ([IMG.LY](https://img.ly/use-cases/server-side-video-rendering/)).
- **Remotion client-side rendering** has been stable since 4.0.491 and runs on Safari 26+. It supports only a CSS subset: no OffthreadVideo, `mix-blend-mode`, `backdrop-filter` or `z-index` ([limits](https://www.remotion.dev/docs/client-side-rendering/limitations)). It could preview or export simple overlays on-device; it is not a final-render path.

## 2. Color (HDR in, SDR out)
- **iPhone HDR** is Dolby Vision 8.4 on an HLG base. In 2023, Meta's pipeline overexposed HDR uploads; it now builds SDR variants with a **tuned Hable** operator and boosts overlays into HDR ([Meta 2023](https://engineering.fb.com/2023/07/17/video-engineering/hdr-video-reels-meta/)).
- **Correction: HDR delivery is not simply "unreliable".** Since November 2025, **Instagram iOS supports DV 8.4 HDR upload and playback** with compressed DV and ambient-viewing metadata, and Meta reports viewers spent more time watching ([Meta 2025](https://engineering.fb.com/2025/11/17/ios/enhancing-hdr-on-instagram-for-ios-with-dolby-vision/)). Two things are unverified: whether the Graph API and Post for Me paths keep HDR, and how the platforms' SDR tone mapping looks. **SDR stays the default; HDR is a tracked experiment.**
- **Reference white.** [ITU-R BT.2408](https://www.itu.int/dms_pub/itu-r/opb/rep/R-REP-BT.2408-8-2024-PDF-E.pdf) puts HLG reference white at a 75% signal = **203 cd/m²**. SDR 100% maps to 75% HLG, and the SDR down-mapper should match the one used for monitoring. Anchor the tone-map A/B there, placing faces and diffuse white correctly. Use the same value for graphics white if HDR ever ships; Meta and HyperFrames already do this.
- **Pipeline (unchanged, refined).** Tone-map once at ingest into an SDR BT.709 mezzanine: libplacebo with DV RPU, `peak_detect=0`, explicit bt709 output and dithering. Blind-A/B it against zscale+tonemap hable and Apple's AVFoundation SDR export. Don't rely on Remotion's untunable zscale.
- **Add a color round-trip test.** Run a chart clip through OffthreadVideo → PNG → bt709 and require near-identity ΔE. This catches #11331/#10841-class regressions.

## 3. Audio and sync
- **Keep the design:** render Remotion **muted** and compile one sample-accurate FFmpeg audio graph from the timeline:
  - `atrim` per kept range, with 5–30 ms fades at cuts
  - rubberband or atempo for speed changes
  - envelope- or sidechain-driven ducking, compiled as sample-rate curves rather than per-frame steps
  - `amix normalize=0`
  - two-pass `loudnorm` with `linear=true`
- **Sync budget (corrected).** ITU-R BT.1359 puts detectability at +45/−125 ms. **EBU R37 allows +40/−60 ms end to end and +5/−15 ms per stage**, and ATSC IS-191 allows at most 45 ms of lag ([A/V sync](https://en.wikipedia.org/wiki/Audio-to-video_synchronization)). The 42.7 ms offset is below detection on its own, but it is about 3× the per-stage budget.
- **No edit lists.** Instagram requires "no edit lists" ([IG](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media)). YouTube advises "No Edit Lists (or the video might not get processed correctly)" ([YouTube](https://support.google.com/youtube/answer/1722171?hl=en)). FFmpeg's mov muxer defaults to `use_editlist=auto` ([formats](https://ffmpeg.org/ffmpeg-formats.html)). So mux with `-use_editlist 0` and **pre-trim the encoder delay**: drop the first N input samples, where N is measured per encoder (2048 for libfdk_aac per #11704). Verify with a beep-and-flash fixture. Do not wait for #11705.
- **Loudness.** No platform publishes a target; −14 LUFS / −1 dBTP is a practitioner convention (weak). The only primary standard, [AES TD1008](https://aes.org/technical-council/technical-document-aestd1008/), recommends **−18 LUFS for speech** (music −16, mixed about −17). A/B −14 against −16 for talking heads, with true peak ≤ −1 dBTP.

## 4. Export settings (primary specs, corrected)
| | Instagram Reels (API) | TikTok (API) | YouTube |
|---|---|---|---|
| Container | MOV/MP4, moov at front, **no edit lists**, **≤300 MB**, 3 s–15 min | MP4 (rec.)/MOV/WebM, ≤4 GB, ≤10 min | MP4, fast start, **no edit lists** |
| Video | HEVC/H.264, closed GOP, 4:2:0, VBR ≤25 Mbps, ≤1920 columns, 23–60 fps | H.264 (rec.)/H.265/VP8/VP9, 23–60 fps, 360–4096 px | H.264 High, **closed GOP of half the frame rate, 2 consecutive B-frames**, CABAC, same fps as recorded; SDR 1080p 8/12 Mbps (no limit required); BT.709 |
| Audio | AAC ≤48 kHz, 1–2 ch, 128 kbps (ads guide: "128kbps minimum") | not specified | AAC-LC 48 kHz, 384 kbps stereo |

Sources: [IG](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media), [Meta ads guide](https://www.facebook.com/business/ads-guide/update/video/instagram-reels), [TikTok](https://developers.tiktok.com/doc/content-posting-api-media-transfer-guide), [YouTube](https://support.google.com/youtube/answer/1722171?hl=en).

**Master encode (corrected).**
- **Settings.** x264 High, 8-bit yuv420p, BT.709 tags, TV range, preset `veryslow`, CRF about 14–16.
- **GOP.** Closed GOP with `keyint = fps/2` and `bf=2`. That matches YouTube and is harmless for Instagram and TikTok.
- **Bitrate cap.** Use `maxrate = min(25 Mbps, IG 300 MB budget)`. That allows about 25 Mbps at 90 s, about 13 Mbps at 3 min and about 3.9 Mbps at 10 min. Consider HEVC for long takes.
- **Other flags.** `+faststart` and the source fps.
- **Intermediate.** Encode once from a ProRes 4444/422HQ intermediate.

**Resolution.** Keep 1080×1920 as the default. Meta's own Reels ads guide recommends **1440×2560**, which fits under the 1920-column cap. Whether 1440-wide uploads deliver better quality is unverified, so A/B it. 4K (2160 wide) breaks the Instagram API limit.

**Platform re-encode.** Instagram assigns encode quality on a **sliding scale by views**: low-view videos get cheaper encodes ([TechCrunch](https://techcrunch.com/2024/10/27/instagram-is-lowering-video-quality-for-unpopular-videos)). QA should therefore also simulate a low-bitrate re-encode and check that captions and faces survive. Score the delivery encode against the master with **VMAF** (libvmaf in FFmpeg; Netflix v3.2.1).

## 5. Safe zones (missed)
- **Meta (official):** keep text and logos out of the **top 14%, bottom 35% and 6% on each side**, about 269/672/65 px at 1080×1920 ([Meta](https://www.facebook.com/business/ads-guide/update/video/instagram-reels)).
- **TikTok and YouTube Shorts:** no public organic figures. Third-party maps put the Shorts right rail at about 120 px and the bottom band at about 350–380 px ([example](https://imagevideofit.com/guides/youtube-shorts-safe-zone)); treat that as weak evidence.
- **How to apply them.** Compile per-platform **protected rectangles** into the render plan. Have the caption and overlay placer respect them, and add a QA check.

## 6. Timeline representation (design stands)
Use an app-owned typed JSON document: tracks → items → assets with stable IDs. A-roll is anchored to word IDs in rational or microsecond source time. Zoom keyframes, a caption token track and audio with ducking specs complete it. One compiler produces a frame-quantized **render plan** consumed by Remotion, the FFmpeg audio graph, iOS preview, QA and the OTIO/FCPXML exporters.

Additions:
1. **Deliverable profiles** as plan inputs: platform, safe-zone rectangles, GOP, bitrate cap, loudness target.
2. **Sample-rate audio automation curves**, not per-frame values.
3. **A pinned color-pipeline version** (tone-map operator and parameters).
4. **Three graphics kinds:**
   - `template` (parameterised)
   - `custom_graphic` (agent-authored React with a Zod schema, a lint/compile check and a rendered-frame check)
   - `lottie`/`rive` assets that iOS can render natively

**iOS preview options, in rising parity:**
1. Native re-implementation (today). It drifts from the server render.
2. AVFoundation base with the same React overlays in a transparent WKWebView, or with Lottie/Rive natively.
3. Remotion Player in a WKWebView. iOS Safari has no Fullscreen API and has autoplay audio limits ([Player](https://www.remotion.dev/docs/player/player)).
4. A commercial same-engine SDK (IMG.LY).

Whichever option is chosen, gate parity by diffing app frames against server snapshots.

## 7. Recommendation (revised)
**Engine.** Remotion as the single compositor, **pinned ≥4.0.527**, with `imageFormat:'png'`, `colorSpace:'bt709'`, OffthreadVideo for finals, `muted:true`, and ProRes output. FFmpeg/libplacebo runs before it (SDR mezzanine, CFR, 48 kHz PCM) and after it: audio graph, own mux without edit lists, pre-trimmed AAC, per-platform encodes. Remotion over HyperFrames still holds, because of typed props, maturity, and HyperFrames' default JPEG pre-extraction. Revisit HyperFrames, or an FFmpeg overlay stage with 203-nit graphics white, if the HDR experiment proves out after checking that the posting path preserves DV 8.4. Keep a watch on #11704/#11705, but do not depend on them.

## Verified recommendations
- Use Remotion as the single compositor, pinned to >=4.0.527 (the first release with the JPEG/bt709 color fix #11331). Set imageFormat 'png' and colorSpace 'bt709' explicitly (the v4 default is bt601), use OffthreadVideo (not @remotion/media) for final renders until frame-diff parity passes, set muted:true, and output a ProRes 4444/422HQ intermediate.
- Add an FFmpeg/libplacebo ingest stage: tone-map iPhone DV 8.4/HLG once to an SDR BT.709 mezzanine (DV RPU applied, peak_detect=0, explicit bt709 output colorimetry, dithering), anchored to BT.2408's 203-nit reference white. Blind-A/B bt.2390 vs hable (vs contrast_recovery 0 and 0.3) vs Apple's AVFoundation SDR export on real Yunicorn takes.
- Take audio out of Remotion entirely: compile one sample-accurate FFmpeg graph (atrim with 5-30 ms fades, rubberband/atempo, sample-rate ducking envelopes rather than Remotion's per-frame volume staircase, amix normalize=0, two-pass loudnorm linear=true). Mux it yourself with -use_editlist 0 and pre-trim the measured encoder delay, since IG forbids edit lists and YouTube advises against them, which rules out Remotion's proposed #11705 fix.
- Encode per-platform from the master: x264 High 8-bit yuv420p BT.709 TV range, veryslow, CRF about 14-16, closed GOP with keyint=fps/2 and bf=2 (YouTube spec), source fps, +faststart, maxrate = min(25 Mbps, the IG 300 MB file budget for the clip's duration), AAC 48 kHz (128 kbps IG, 384 kbps YouTube). A/B 1080x1920 against 1440x2560 (Meta's recommended ads resolution, within IG's 1920-column cap).
- Compile per-platform safe zones into the render plan as protected rectangles (Meta official: 14% top, 35% bottom, 6% sides; TikTok and Shorts from maintained templates) and have caption and overlay placement plus QA enforce them.
- Treat loudness as a tunable deliverable parameter: A/B -14 LUFS against -16 LUFS integrated (AES TD1008 recommends -18 for speech; no platform publishes a target), with true peak <= -1 dBTP.
- Run output QA on every final file: ffprobe color tags (bt709/tv), CFR and fps, absence of edit lists, file size vs the IG 300 MB cap, measured A/V offset (beep-and-flash fixture, target within the EBU R37 per-stage budget of +5/-15 ms), integrated loudness and true peak, a color round-trip chart check, VMAF of the delivery encode vs the master and of a simulated low-bitrate platform re-encode, and safe-zone collision checks.
- Keep the app-owned typed JSON timeline, compiled to a single frame-quantized render plan. Add deliverable profiles, sample-rate audio curves and a pinned color-pipeline version to the plan, and support three graphics kinds: template, sandboxed custom_graphic (Zod schema, compile check, rendered-frame check) and Lottie/Rive assets that iOS can render natively.
- For iOS preview parity, replace the native overlay re-implementation with either shared React overlays in a transparent WKWebView over AVFoundation or Lottie/Rive assets rendered natively (evaluate IMG.LY CE.SDK only if exact same-engine parity outweighs arbitrary CSS/React graphics). Gate any of these with automated frame diffs against server snapshots.
- Keep SDR as the default deliverable, but run HDR as a tracked experiment rather than ruling it out. Instagram iOS has supported DV 8.4 HDR since November 2025. First confirm whether the Graph API and Post for Me paths preserve HDR; if they do, prototype HDR compositing with HyperFrames (libx265, not hardware HEVC) or an FFmpeg overlay stage, with graphics white at 203 nits.

## Tools
- Remotion [Programmatic compositor (React + headless Chrome + FFmpeg); Custom source-available: free for individuals and companies of up to 3 people; Company License otherwise ($0.01/render with a $100/mo minimum, or $25/seat/mo)] https://www.remotion.dev — 60.8k stars; v4.0.529 (2026-09-25). OffthreadVideo extracts exact lossless BMP frames; supports bt709 and 10-bit pixel formats. Known issues: JPEG q80 default, bt601 default in v4, no HDR, 42.7 ms AAC lag (#11704 open), JPEG+bt709 bug fixed 2026-09-18 (#11331). Recommended primary compositor, rendered muted with the audio mixed in FFmpeg.
- HyperFrames [Programmatic compositor (HTML/GSAP + headless Chrome beginFrame + FFmpeg); Apache-2.0] https://github.com/heygen-com/hyperframes — 53.7k stars; v0.8.81 (2026-09-27); created 2026-03. CRF 16 default, png video-frame extraction option, ProRes 4444. Native HDR10/HLG 10-bit HEVC output with SDR DOM composited into HDR (not on Lambda). Deterministic only on Linux; ±1-level pixel variance across workers. Strongest alternative; re-evaluate if HDR delivery is wanted.
- FFmpeg (zscale, libplacebo, loudnorm, sidechaincompress, x264) [Ingest normalization, audio mixing, final encode; LGPL-2.1+ (GPL when built with libx264)] https://ffmpeg.org/ffmpeg-filters.html — libplacebo applies Dolby Vision RPU and supports bt.2390/st2094 tone mapping; frame- and sample-accurate trims. Traps: zoompan rounds to whole pixels (jitter), amix normalizes by default, libass captions allow only one move tag per line. Use before and after the compositor, not as the compositor.
- libplacebo [HDR tone mapping and high-quality scaling (via FFmpeg filter); LGPL-2.1+] https://libplacebo.org/options/ — GPU tone mapping with bt.2390/st2094, DV RPU, dithering and contrast recovery; recommended by practitioner guides for premium SDR derivation (weak evidence). Set peak_detect=0 for reproducible output.
- OpenTimelineIO [Timeline interchange (export); Apache-2.0] https://github.com/AcademySoftwareFoundation/OpenTimelineIO — ~2k stars; v0.18.1; last push 2026-09-26. Effects and spatial transforms are not supported natively (per prior notes). Export cuts, linear speed and markers only.
- FCPXML [Pro NLE handoff format (export); Apple format specification] https://developer.apple.com/documentation/professional-video-applications/document-type-definition — Has caption/title elements, keyframed adjust-transform and adjust-volume, and connected-clip lanes (per prior notes). Richest export target for rich creator edits.
- MLT / melt (Shotcut engine) [NLE engine with XML timeline; LGPL-2.1] https://github.com/mltframework/mlt — v7.40 (2026-06). Shotcut 25.12 added 10-bit linear CPU processing (not all filters converted); Shotcut 26.6 added HLG/PQ HDR export. Weak text and motion graphics; not recommended as primary.
- GStreamer Editing Services [NLE engine library; LGPL-2.1+] https://gitlab.freedesktop.org/gstreamer/gstreamer — Shipped in GStreamer 1.28.7 (2026-09-07); Pitivi's last tagged release is 2023.03; thin ecosystem. Not recommended.
- MoviePy 2.x [Python compositing library; MIT] https://github.com/Zulko/moviepy — v2.2.1 (2025-05-21). A user reported v2 more than 10x slower than v1 (#2395). Numpy frame compositing; no documented color management. Prototype use only.
- Editly [Declarative JSON video editor (FFmpeg + canvas/Fabric/GL); MIT] https://github.com/mifi/editly — 5.5k stars; last code commit 2025-02; audio ducking/normalization via dynaudnorm. Stale; not recommended.
